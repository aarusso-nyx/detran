### 2.2 `Idempotency-Key` determinística — transcrição de `plan.md` M17

> Forma `<ato>:<alvo>:<fingerprint>` com `<ato>` = `serviceKey` (ou `withdraw`, `respond_diligence`,
> `elevation`), `<alvo>` = id do recurso alvo (`aitId`, `requestId`, `diligenceId`) e
> `<fingerprint>` = SHA-256 (hex minúsculo, 64 caracteres) do corpo JSON canonicalizado — chaves
> ordenadas recursivamente, sem espaços, `undefined` omitido, UTF-8 — calculado no cliente com
> `crypto.subtle`. Mesmo corpo → mesma chave; corpo diferente → chave diferente (o backend
> responde 409 `IDEMPOTENT_KEY_REUSE_DIFFERENT_BODY` ao reuso divergente).

```ts
// data/idempotency-key.ts
/** JSON canônico (M17): objetos com chaves em ordem de código de unidade (Array#sort sem
 *  comparador), recursivo; arrays na ordem dada; `undefined` (e funções) omitidos como em
 *  JSON.stringify; `null` mantido; sem espaços; números/strings como JSON.stringify. */
export function canonicalJson(value: unknown): string;
/** SHA-256 via crypto.subtle.digest sobre UTF-8 (string) ou bytes; hex minúsculo, 64 chars. */
export function sha256Hex(
  input: string | ArrayBuffer | Uint8Array,
): Promise<string>;
/** `${act}:${target}:${await sha256Hex(canonicalJson(body))}`. */
export function idempotencyKey(
  act: string,
  target: string,
  body: unknown,
): Promise<string>;
```

Matriz `<ato>`/`<alvo>` por comando (M17 fixa as quatro primeiras linhas; as demais são extensão
deste contrato para os comandos que o kernel também exige idempotentes — [DIVERGE-5] e [DIVERGE-6]):

```text

                                                    `defesa_previa:<aitId>:<fp>`)
```

### 2.3 `If-Match`/`ETag` e o resultado de comando

```ts
// data/portal-command.models.ts
export interface CommandResult<T> {
  readonly body: T;
  /** Cabeçalho `ETag` da resposta, tal como recebido (`"<version>"`, com aspas), ou `null`. */
  readonly etag: string | null;
}
/** `"<version>"` — forma do ETag do contrato (OpenAPI: `ETag: "<version>"`). */
export function etagOf(version: number): string;

// Formas 2xx ausentes do OpenAPI (OD-P59; derivadas de portal-route-contract.md §3/§5):
export interface AttachmentUploadIntent {
  readonly attachmentId: string; // source_pending: nome do campo
  readonly uploadUrl: string; // "URL assinada" (§5)
  readonly method: 'PUT'; // source_pending
  readonly headers: Readonly<Record<string, string>>; // source_pending
  readonly expiresAt: string | null; // source_pending
}
export interface AttachmentCompleted {
  readonly attachmentId: string;
  readonly sha256: string; // "anexo com hash" (§5)
}
export interface DiligenceResponded {
  readonly requestId: string;
  readonly version: number; // source_pending ("status muda na hora", §5)
}
export interface ElevationStarted {
  readonly redirectUrl: string; // §3
  readonly resumeToken: string; // §3
  readonly elevationId: string; // source_pending: `{id}` de …/elevations/{id}/complete ([DIVERGE-14])
}
export interface ElevationCompleted {
  readonly assuranceLevel: 'simples' | 'avancada' | 'qualificada'; // "nível atualizado a partir da claim" (§3)
}
```

`If-Match` é sempre o `etag` lido do último `CommandResult` do mesmo pedido (ou `etagOf(version)`
quando a resposta trouxe `version` no corpo e não o cabeçalho). O cliente **nunca inventa** versão:
o parâmetro `ifMatch: string | null` com `null` omite o cabeçalho e o servidor responde
`428 PORTAL.IF_MATCH_REQUIRED`, propagado ao `ErrorBoundary` (§3). `412 PORTAL.VERSION_CONFLICT` →
apresentação `nextStep: 'reload'`.

Regras de implementação: todo comando usa o `HttpClient` de `provideStynxDefaults` com
`observe: 'response'` para ler `ETag`; `Idempotency-Key` é calculada com `idempotencyKey()` antes
do envio e recalculada a cada chamada (mesmo corpo → mesma chave, o servidor reproduz a resposta);
`uploadToSignedUrl` usa `fetch` puro (sem os interceptors STYNX) para não vazar o bearer ao storage
([DIVERGE-17]); `downloadReceipt` passa pelo `HttpClient` (o recibo exige sessão). Nenhum método
captura erros: a promessa rejeita com o `HttpErrorResponse` original e o chamador classifica com
`presentError` (§3). Exceções de rede (status 0) também sobem intactas.

`true` → `load()`; transição `true → false` → `account.set(null)` **e** `OfflineDocumentStore.clear()`

toca em `window.location`. Após `completeElevation`, o chamador lê `ResumeService.peek()` para

`prefilled`, `requirements`, `minimumAssurance`; `409 REQUEST_DRAFT_EXISTS` → `error` com
`nextStep: 'existing_request'` (T02 §5 "direciona ao processo existente"); `422 INELIGIBLE` →
`status = 'ineligible'` + `ineligible` emitido (motivo e alternativa, nunca "acesso negado");
`422 SERVICE_UNAVAILABLE` → `status = 'unavailable'`. `save()` → `schema.safeParse(values())`:
inválido → `fields` para a diretiva **sem** requisição (validação de forma só orienta, M12);
válido → `saveDraft(requestId, serviceKey, values, etag)`; 200 → `etag` atualizado. Rascunho
**só no servidor** (spec §1 "Estado"); um por ato e alvo (spec §8). `sign()` → se `consequence`
foi dado e `ack` é `null`, não envia (o diálogo é etapa própria); `submitRequest(requestId,
serviceKey, targetId, { signature, consequenceAck })`; 200 → `receipt`, `step = 'protocolo'`,
`status = 'done'`; `403 ASSURANCE_INSUFFICIENT` → `ResumeService.save({ route: resumeRoute, draft:
WizardResumeDraft })` e `elevationRequested` (via `SignatureStep`); `502 DELEGATION_FAILED` →
`step = 'protocolo'` com o recibo de `context.protocol` e banner `warning` (protocolo é imediato,
[RN-PORTAL-111] 1); `422 REQUEST_CONSEQUENCE_ACK_REQUIRED` → permanece em `assinatura` com o banner.
`resumeFrom(point)` → restaura `requestId`, `etag`, `step`, `values` sem chamar `createRequest`
([UC-PORTAL-019] AC-4). Aviso `REQUEST_OUT_OF_DEADLINE`: o servidor protocola e avisa (spec §7); a
forma pela qual o aviso chega no 200 é `source_pending` (OD-P59) — quando chegar, é exibido como
`warning` sem alterar o passo. Offline (`navigator.onLine === false` ou status 0) →
`status = 'offline'` com `portal.states.offline`, sem fila nem promessa de envio posterior (spec
§8). Todo passo renderiza `portal-alternative-channel-note` ([RN-PORTAL-105]; invariante 6) e o
checklist de `requirements` aparece inteiro no passo 2 ([RN-PORTAL-107] regra 3). Rótulos do
próprio wizard (nomes dos passos, `aria-label` da navegação de passos, "rascunho salvo"): OD-P58.

## 7. `OfflineDocumentStore` (M14) — contrato testável

```ts
export type OfflineDocumentKind = 'cnh-e' | 'crlv-e'; // únicos conteúdos offline (spec §1; [UC-PORTAL-011] AC-4)
export interface OfflineDocument<T = unknown> { kind; document: T; validUntil: string }
put<T>(kind, document: T, validUntil: string): Promise<void>;
get<T>(kind, now?: Date): Promise<OfflineDocument<T> | null>; // now default = PortalClock.now()
clear(): void;
```

Invariantes (código existente mantido; testes novos):

1. Chave AES-GCM-256 derivada por HKDF (SHA-256, salt `portal-offline-document-v1`, info
   `portal-offline-document`) do `sid` da sessão STYNX, `extractable: false`, só em memória; sem
   `sid` → `put` não grava e `get` devolve `null`.
2. O que vai ao armazenamento é `{ iv, payload }` em base64 (IV de 12 bytes aleatórios por
   gravação); o JSON do documento **nunca** aparece em claro em `sessionStorage` (Riscos do plano).
3. `get` devolve `null` e remove a entrada quando `validUntil <= now` (validade retornada pelo
   servidor; nunca calculada), quando o `sid` mudou (decifração falha) ou quando o envelope está
   corrompido.
4. `clear()` remove as duas entradas e a chave em memória; é chamado no logout pela
   `PortalSessionFacade` (§4) e pode ser chamado por T-16/T-17 (par 3).
5. Persistência do texto cifrado: `sessionStorage` (morre com a aba) até OD-P51 decidir IndexedDB;
   `dataGroups` do `ngsw-config.json` não entram aqui (A3(a)).
6. "Modo bateria crítica" (spec §5.1, [JRN-PORTAL-006]): [UC-PORTAL-011] AC-4 fixa apenas que a
   CNH-e "abre e é verificável sem rede"; limiar de bateria e autenticação local **não têm fonte**
   → `source_pending` (OD-P54). Nenhuma API é definida para isso neste par; o Inspector registra
   `it.todo('OD-P54')`.
7. Nenhuma outra rota tem cache offline: fora de T-16/T-17 o app mostra `portal.states.offline` sem
   prometer envio posterior (spec §8; §5.4).
