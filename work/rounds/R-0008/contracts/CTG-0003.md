## 1. Máquina de estados da evidência — `ops.evidence_evidence.status`

Conjunto fechado pelo check `ck_ops_evidence_status` do `BP-OPS-EVIDENCE-001` (nove tokens). Não
é um workflow do corpus: é vocabulário de modelagem da custódia, e os tokens são os do
blueprint, não tokens canônicos de `docs/framework/product`.

```text
from             → to              : comando              : guarda
---------------    --------------    -------------------    ------------------------------------
(nenhum)         → pending_upload   : upload-intents       : hash_value presente; entidade aplicada
pending_upload   → uploaded         : complete-upload      : intenção não expirada; hash confere
uploaded         → validated        : validate             : decisão `valid`
uploaded         → rejected         : validate             : decisão `invalid`
uploaded         → linked           : links                : vínculo criado (route contract §4.4)
validated        → linked           : links                : idem
validated        → packaged         : probative-packages   : item entra no pacote
linked           → packaged         : probative-packages   : idem
pending_upload   → rejected         : purge-expired-       : intenção expirada e não bodycam
                                      unverified
qualquer         → quarantined      : (custódia)           : sem rota nesta rodada — §11.1
packaged         → archived         : (retenção)           : sem rota nesta rodada — §11.1
qualquer         → superseded       : (substituição)       : sem rota nesta rodada — §11.1

estados não admitidos por comando
comando                     admitidos                        negados
--------------------------  -------------------------------  -------------------------------------
complete-upload             pending_upload                   os outros 8
validate                    uploaded                         os outros 8 (quarantined → 409
                                                             TEAT.EVIDENCE_QUARANTINED, precede)
links                       uploaded, validated              os outros 7
custody-events              todos                            —
probative-packages/generate (sobre a entidade, não a evidência: exige ≥1 evidência
                             validated|linked — §4.6)
purge-expired-unverified    pending_upload                   os outros 8
```

Acesso a conteúdo de bodycam — `ops.evidence_access_request.status`, check
`ck_ops_evidence_access_status` (quatro tokens):

```text
from       → to         : comando    : guarda
---------    ---------    ---------    -----------------------------------------------
(nenhum)   → requested   : create     : requester_role ∈ rol do art. 13 (RN-TEAT-142)
requested  → approved    : approve    : —
requested  → denied      : deny       : —
approved   → delivered   : deliver    : delivery_media_ref presente (check
                                        ck_ops_evidence_access_delivered_complete)

comando    admitidos    negados                → 409 TEAT.EVIDENCE_ACCESS_STATE_INVALID
---------  -----------  ---------------------------------------------------------------
approve    requested    approved, denied, delivered
deny       requested    approved, denied, delivered
deliver    approved     requested, denied, delivered
```

## 2. Máquina de estados do catálogo e do pacote — [WF-TEAT-003] transcrita

```text
catálogo — inf.normative_catalog.status
armazenado  domínio        significado
----------  -------------  ------------------------------------------
draft       RASCUNHO_CAT   em edição
active      ATIVO_CAT      vale para novos atos
retired     RETIRADO_CAT   não referenciável em novos atos

from    → to       : comando               : guarda
-------   --------   -------------------     ----------------------------------
draft   → active    : catalogs/{id}/publish : —
active  → active    : catalogs/{id}/publish : idempotente (WF: "de draft/active")
active  → retired   : catalogs/{id}/retire  : —

comando   admitidos       negados → 409 TEAT.CATALOG_STATE_INVALID
--------  --------------  ------------------------------------------
publish   draft, active   retired
retire    active          draft, retired

pacote — inf.normative_mobile_package.status
armazenado  domínio         significado
----------  --------------  ------------------------------------------------------
draft       RASCUNHO_PKG    derivado de catálogo ativo, com manifesto
published   PUBLICADO_PKG   distribuível pelo sync-metadata
retired     RETIRADO_PKG    retirado

VALIDADO_PKG do [WF-TEAT-003] é nome de domínio e **não persiste**: `validate` é idempotente,
devolve { valid, reason } e nunca muda `status` (M13). O desenho `PUBLICADO_PKG → VALIDADO_PKG →
PUBLICADO_PKG` do workflow é, no armazenamento, um ciclo sobre `published`.

from      → to         : comando                       : guarda
---------   ---------    ---------------------------     --------------------------------------
(nenhum)  → draft       : mobile-packages/generate      : catálogo `active`
draft     → published   : mobile-packages/{id}/publish  : catálogo `active`; manifest_hash confere
published → published   : mobile-packages/{id}/publish  : idempotente (WF: "de draft/published")
published → published   : mobile-packages/{id}/validate : idempotente, sem mudança
published → retired     : mobile-packages/{id}/retire   : —

comando   admitidos          negados → 409 TEAT.PACKAGE_STATE_INVALID
--------  -----------------  -----------------------------------------
generate  (cria)             —  (falha do catálogo → 422 TEAT.PACKAGE_CATALOG_NOT_ACTIVE)
publish   draft, published   retired
retire    published          draft, retired
validate  draft, published,  —  (é idempotente em qualquer estado; `valid:false` com motivo
          retired                quando o estado não é `published`)
content   published          draft, retired → 409 TEAT.PACKAGE_STATE_INVALID
```

## 13. Divergências encontradas

1. **Três estados de evidência sem comando.** `quarantined`, `archived` e `superseded` estão no
   check do blueprint e nenhuma rota do route contract §4.4 os alcança. Nesta rodada só existem
   por fixture (e `quarantined` como pré-condição de bloqueio). `source_pending`. → **OD-T30**.
2. **Catálogo de `evidence_type` inexistente.** `TEAT.EVIDENCE_TYPE_NOT_IN_CATALOG` exige um rol,
   e não há tabela nem parâmetro que o defina em nenhum blueprint. A guarda fica declarada e
   **desligada** nesta rodada (`source_pending`), com o código reservado. → **OD-T31**.
3. **`evidence_evidence.storage_uri` é `not null`.** M11 manda `storage_uri = null` em
   `pending_upload`. Como o blueprint não admite, a linha nasce com
   `storage_uri = storage_intent.object_key`, que é a chave já decidida por M11 e não afirma que
   o upload ocorreu (o `status='pending_upload'` é quem diz isso). Tornar a coluna anulável é
   delta de `BP-OPS-EVIDENCE-001` fora desta tarefa. → **OD-T32**.
4. **Índice único `(tenant_id, hash_value)`.** Dois arquivos idênticos no mesmo tenant não podem
   coexistir como evidências distintas — é deduplicação por conteúdo, não decisão de produto.
   Consequência fixada na §4.1 (409 `TEAT.IDEMPOTENCY_REPLAY`). Registrado.
5. **Catálogo sem `TEAT.EVIDENCE_STATE_INVALID`.** Estado inválido de evidência sai como 422
   `TEAT.VALIDATION_FAILED { fields:[{ path:'status', rule:'transition' }] }`, nunca um código
   novo. Mesma solução da reserva de numeração (CTG-0002 §11.12). → **OD-T29**.
6. **`validate` devolve `invalid` no route contract e `rejected` no blueprint.** O check
