```text
export class DetranError extends StynxError            // @stynx-nyx/core
  constructor(code: string, options: {
    status: number;
    context?: Record<string, unknown>;   // só ids, tokens canônicos e números (§1 regra 4)
    message?: string;                    // fallback pt-BR; default = o próprio code
    cause?: unknown;
  })
  declare readonly context: Record<string, unknown>;
  this.name = 'DetranError'

messageKey  = '<prefixo minúsculo>.errors.<código sem prefixo, minúsculo>'
              TEAT.AIT_STATE_INVALID  → teat.errors.ait_state_invalid
              RAIT.CASE_STATE_INVALID → rait.errors.case_state_invalid
              a derivação é `code.replace(/^[A-Z]+\./, '')` minúsculo, prefixada pelo
              segmento anterior ao ponto, também minúsculo — nunca uma tabela literal

export function assertIfMatch(
  header: string | string[] | undefined,
  version: number,
  prefix: 'TEAT' | 'RAIT',
): void
  header ausente/vazio       → DetranError('<PREFIX>.IF_MATCH_REQUIRED', { status: 428 })
  header mal formado         → DetranError('<PREFIX>.IF_MATCH_REQUIRED', { status: 428 })
  header ≠ String(version)   → DetranError('<PREFIX>.VERSION_CONFLICT',  { status: 412,
                                 context: { expected: version } })
  formas aceitas: `17`, `"17"`, `W/"17"` (mesma gramática de
  OpsParameterService.normalizeIfMatch, parameter.service.ts)

export function etagOf(version: number): string   // `"<version>"`, com as aspas
```

Códigos do envelope: `TEAT.IF_MATCH_REQUIRED` 428 e `TEAT.VERSION_CONFLICT` 412 existem no
`teat-error-catalog.md` §9; `RAIT.*` equivalentes existem no `rait-error-catalog.md`.

```text
export interface TeatEventEnvelope {                 // rait-events-sse-contract.md §1
  id: string;                                        // ULID da linha da outbox
  type: string;                                      // técnico (§7 do route contract)

  correlationId: string;                             // requestId do comando

  data: Record<string, unknown>;                     // só ids, tokens e datas
}

  append(tx: Transaction, envelope: TeatEventEnvelope): Promise<void>;
}
export const TEAT_EVENT_OUTBOX: unique symbol;       // token de injeção Nest
```

Implementação `SqlTeatEventOutbox` (`backend/domains/shared/src/events/sql-outbox.ts`), gravada na
**mesma transação** do comando, em `integration.outbox` (DDL 04):

```text
coluna outbox      valor
-----------------  --------------------------------------------------------------
tenant_id          envelope.tenantId
topic              envelope.type
aggregate_type     envelope.aggregate.kind
aggregate_id       envelope.aggregate.id
payload            o envelope inteiro, como jsonb
idempotency_key    '<type>:<aggregate.id>:<aggregate.version>'
status             'pending'   (default do DDL)
available_at       envelope.occurredAt
```

`unique (tenant_id, idempotency_key)` do DDL 04 é a idempotência do append: reemitir o mesmo
evento para a mesma versão do agregado é `on conflict do nothing`. `integration.outbox.id` é
`uuid default gen_random_uuid()`, **não** um ULID — divergência §11.1: `envelope.id` é o `id`
devolvido pelo `insert … returning id` e a ordem do stream é `(created_at, id)`, nunca a ordem
lexicográfica de ULID prometida pelo §1 do contrato de eventos.

## 11. Divergências encontradas (documento × decisão M × código atual)

1. **`integration.outbox.id` não é ULID.** `rait-events-sse-contract.md` §1 promete um ULID que
   ordena por tempo; o DDL 04 define `uuid default gen_random_uuid()`. O `id` do SSE e o replay
   por `Last-Event-ID` passam a ordenar por `(created_at, id)` (M17 já diz isso). Nenhuma
   invenção: o contrato de eventos é que está desatualizado. → **OD-T19**.
2. **`RECEBIDO → VALIDANDO` e `INTEGRADO → PROCESSADO` não têm comando.** [WF-TEAT-001] as
   desenha, o route contract §3.2 não lhes dá rota e nenhuma decisão M as cobre. Nesta rodada
   **não existem**: `VALIDANDO` e `PROCESSADO` só são alcançáveis por fixture, e `accept` aceita
   `VALIDANDO` como pré-estado sem que haja como chegar lá pela API. `source_pending`. →
   **OD-T20**.
3. **`ait.changed` sem token de domínio.** O route contract §7 lista `ait.changed` como tipo SSE,
   mas o §8 nomeia só seis tokens do AIT. Oito transições (`ENFILEIRADO`, `VALIDANDO`,
   `PENDENTE_CORRECAO`, `CORRIGIDO`, `PROCESSADO`, `ARQUIVADO`, `CANCELADO_RASCUNHO`,
   `SOLICITADO_CANCEL_POSFINAL`) **não publicam evento** nesta rodada, porque o §8 é lista
   fechada e inventar token é proibido. A UI recarrega o recurso nesses casos. → **OD-T21**.
4. **`ait_print_event.event_type` sem vocabulário.** Sem check no blueprint e sem tabela de
   referência. Fixado aqui como vocabulário de modelagem (`impressao`, `reimpressao`, `falha`),
   no precedente de `work/rounds/R-0006/contracts/CTG-0001.md` §2 — não é token canônico e não
   entra em `verify:lifecycle-vocabulary`.
5. **`approveCorrection` mais largo que o contrato.** `ait-lifecycle.service.ts` admite
   `PENDENTE_CORRECAO` **e** `CORRIGIDO`; o route contract §3.2 admite só `PENDENTE_CORRECAO`.
   Prevalece o documento canônico; o Engineer estreita a guarda (efeito colateral: o teste
   existente `ait-lifecycle.service.spec.ts` que exercita `CORRIGIDO` precisa mudar — é o
   Inspector de TASK-0002 que o reescreve, nunca o Engineer).
6. **`BP-INF-AIT-001` não sustenta o cancelamento.** `inf.ait_cancel_request` tem
   `ait_id uuid not null` e `target_local_act_id varchar(120)` **anulável** — exatamente o
   inverso do que M4 e o DTO da origem exigem — e **não tem** as colunas `idempotency_key`,
   `justification`, `requested_by`, `legal_basis_note`, `decision_body`,
   `decision_legal_basis`, `linked_measure_decision` nem `version`. Consequências fixadas neste
   contrato, para que TASK-0002/0003 não parem:
   - `justification`, `legalBasisNote`, `idempotencyKey`, `targetReservedNumber`,
     `targetContentHash`, `location`, `decisionLegalBasis`, `decisionBody` e
     `linkedMeasureDecision` vivem em `ait_cancel_request_event.details_json`;
   - a idempotência de `POST cancel-requests` é verificada por varredura de
     `ait_cancel_request_event.details_json->>'idempotency_key'` no tenant — **sem índice**, o
     que é aceitável no volume de fixtures e inaceitável em produção;
   - `If-Match` de `review`/`decide` usa `ait_ait.version`, e não uma versão do pedido;
   - `ait_id` **precisa** tornar-se anulável para o caminho 202 de M4.
     Isso exige um delta `BP-INF-AIT-001` v1.2.0 no bloco `database.entities` que **está fora da
     fronteira de escrita desta tarefa** e não foi atribuído a nenhuma tarefa de R-0008. É um
     bloqueio para TASK-0003 e vai à triagem do maestro. → **OD-T22**.
7. **Quatro recursos gerados sem regra de política.** `ait-cancel-request`,
   `ait-cancel-request-event`, `normative-metrological-table` e `signature-policy` têm
   controlador CRUD gerado com `@Resource`/`@Action` e **não** estão em `INF_RESOURCES`: hoje
   `isDetranActionAllowed` devolve `false` para todos os papéis que não sejam admin global. O
   `policy-routes.e2e.spec.ts` de M18 falharia no sentido rota → regra. Correção na §5.
