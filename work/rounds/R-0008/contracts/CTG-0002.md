## 2. Máquina de estados da numeração — [WF-TEAT-002] transcrita

Duas entidades. Os tokens do workflow (`ATIVA`/`ESGOTADA`, `RESERVADA`/`CONSUMIDA`/`EXPIRADA`/
`CANCELADA`) são os nomes de domínio; o armazenado é o do blueprint, como o próprio
`25-fixtures-teat.sql` já anota.

```text
faixa — ops.ait_numbering_range.status
armazenado  domínio     significado
----------  ----------  -------------------------------------------------------------
active      ATIVA       aceita novas reservas
exhausted   ESGOTADA    último número alocado = end_number (M8)

from     → to          : comando               : guarda
-------    ----------    --------------------    -----------------------------------------
(nenhum) → active       : POST numbering-ranges : start_number ≤ end_number (check do DDL 18)
active   → active       : reserve               : next_number + requested_size − 1 ≤ end_number
active   → exhausted    : reserve               : next_number + requested_size − 1 = end_number
exhausted→ active       : cancel               : só quando a reserva cancelada é a cauda da
                                                  faixa e next_number recua (M8)
```

O check `ck_ops_ait_numbering_range_bounds` exige `next_number between start_number and
end_number`, logo `next_number > end_number` é impossível: a forma de OD-T07 "next_number atinge
end_number" realiza-se como "o último número alocado é `end_number`" e `next_number` permanece em
`end_number` com `status='exhausted'`. Nota obrigatória do Engineer no código (M8).

```text
reserva — ops.numbering_reservation.status
armazenado  domínio     significado
----------  ----------  -------------------------------------------------------------
reserved    RESERVADA   subintervalo alocado e vigente
consumed    CONSUMIDA   fechada com consumo (close)
expired     EXPIRADA    valid_until atingido sem consumo total
cancelled   CANCELADA   cancelada; cauda devolvida à faixa quando aplicável
blocked     —           bloqueada por decisão administrativa (sem token no WF; §11.2)

from      → to        : comando   : guarda
---------   ---------   --------    --------------------------------------------------------
(nenhum)  → reserved   : reserve   : faixa active; sem reserva reserved do mesmo device+shift
reserved  → cancelled  : cancel    : existe ao menos um número não consumido
reserved  → blocked    : block     : status ∉ {cancelled, consumed}
reserved  → consumed   : close     : status ∉ {cancelled, blocked}
reserved  → expired    : (varredura): valid_until < now() — **não há rota**; §11.3
reserved  → reserved   : reconcile : claimed_numbers ⊆ [start_number, end_number]
```

Estados **não** admitidos por comando (casos 409/422 do Inspector):

```text
comando     admitidos                 negados
----------  ------------------------  ---------------------------------------------------
cancel      reserved                  consumed, expired, blocked (cancelled → idempotente,
                                      devolve a própria reserva)
block       reserved, expired         cancelled, consumed (blocked → idempotente)
close       reserved, expired         cancelled, blocked (consumed → idempotente)
reconcile   reserved, consumed        cancelled, blocked, expired
consumption (leitura: todos)          —
```

## 3. Consumo por número — `ops.numbering_consumption.status`

Conjunto do route contract §4.3, fechado, com seis tokens:

```text
disponivel             número da reserva não reclamado pelo dispositivo e sem AIT no servidor
consumido_localmente   reclamado pelo dispositivo, sem AIT aplicado no servidor
aplicado               AIT aplicado no servidor consumiu o número (M7)
inutilizado            número inutilizado no dispositivo (só chega por reconcile explícito)
expirado               reserva expirou antes de o número ser usado
bloqueado              reserva bloqueada antes de o número ser usado
```

`ops.numbering_consumption` tem três índices únicos por tenant — `(range_id, number)`,
`(local_entity_id)` e `(idempotency_key)`. O primeiro é a garantia de que **um número nunca é
reatribuído**; o terceiro é a idempotência do applier. As colunas `local_entity_id`,
`idempotency_key`, `server_entity_id` e `finalized_at` são **not null** no blueprint, o que
impede gravar uma linha `disponivel` ou `expirado` sem um ato correspondente — §11.4.

## 4. Protocolo de sincronização (M5–M8) — algoritmo normativo

`POST /v1/ops/offline-sync/sync-batches` é o único ponto de entrada. Tudo abaixo é a definição
que o Inspector transcreve em testes e o Engineer em código; nenhuma etapa é opcional e a ordem
é parte do contrato.

### 4.1 Lote — passos, em ordem

```text
 1. autenticação, política (ops:sync-batch:submit) e tenant do RequestContext
 2. lock de escopo: `select … from ops.sync_batch where tenant_id = $1 and device_id = $2
    for update` (serializa a aceitação por tenant+device; espelho de lockSyncBatchScope)
 3. replay de lote: já existe sync_batch com (tenant_id, device_id, device_batch_id)?
      3a. batch_sequence informado ≠ o gravado          → 409 SYNC_BATCH_REPLAY_CONTEXT_MISMATCH
      3b. conjunto de idempotency_key (ordenado) ≠ o gravado
                                                        → 409 SYNC_BATCH_REPLAY_CONTEXT_MISMATCH
      3c. iguais                                        → 200 com os recibos originais, **sem
                                                          tocar em estado de domínio**
 4. sequência (só para device_batch_id novo, e só quando batch_sequence vem no corpo):
      last = max(batch_sequence) aceito do (tenant, device), ou 0
      batch_sequence ≤ last        → 409 SYNC_BATCH_SEQUENCE_REPLAYED
                                     { expectedSequence: last + 1, received }
      batch_sequence > last + 1    → 422 SYNC_BATCH_SEQUENCE_GAP
                                     { expectedSequence: last + 1, received }
      batch_sequence ausente       → caminho legado: durável, **sem** garantia de ordem
 5. materialização dos itens: para cada item, cria ou reusa ops.sync_queue_item (§4.2)
 6. detecção de concorrência sobre os itens `ait` do lote (§4.7)
 7. aplicação item a item (§4.3), **uma transação por item**
 8. recibos: ops.sync_receipt por item; accepted_items = recibos cujo status ∉
    {rejected, conflict}
 9. grava ops.sync_batch { device_batch_id, batch_sequence, submitted_at, accepted_items,
    receipts_json = { item_ids: [...] } }
10. evento de lote sync.batch.received e um SYNC_ITEM_RECEBIDO por item (§7)
11. resposta 200
```

O passo 3 precede o 4 de propósito: a retransmissão de rede do último lote aceito é um replay,
nunca uma violação de sequência.

### 4.2 Item — identidade e integridade

```text
idempotency_key ausente
  → chave derivada `legacy:<device_id>:<local_entity_id>`
  → ops.sync_queue_item gravado com status 'received'
  → recibo `received` com reason_code TEAT.SYNC_LEGACY_ITEM_NOT_APPLIED
  → **nunca** aplicado: não há garantia de exatamente-uma-vez sem chave estável

idempotency_key presente e já vista no tenant
  payload_hash igual     → devolve o recibo existente; nenhum efeito novo
  payload_hash diferente → recibo `rejected`, reason_code TEAT.SYNC_INTEGRITY_ERROR,
                           context { idempotencyKey, storedHash, receivedHash }
                           + ops.sync_conflict { conflict_type:'integrity',
                             reason_code:'TEAT.SYNC_INTEGRITY_ERROR',
                             local_hash: receivedHash, server_hash: storedHash,
                             retryable: false, allowed_resolution_actions:
                             ['accept_server','reject','retry_after_correction'],
                             status:'open' }

payload_hash do corpo ≠ sha256 canônico de payload_json
  → o mesmo TEAT.SYNC_INTEGRITY_ERROR (o hash é do cliente e é conferido no servidor)
```

Hash canônico = `sha256` do JSON com chaves ordenadas recursivamente e sem espaços — a mesma
`stableJson` já usada por `contentHashForAit` em `ait-lifecycle.service.ts`. Prefixo `sha256:`
obrigatório na coluna, como nas fixtures.

### 4.3 Item — aplicação

```text
1. entity_type ∉ lista suportada
     → recibo `rejected`, TEAT.SYNC_UNSUPPORTED_ENTITY_TYPE { supported: [...] }
2. entity_type suportado sem applier montado (falha de implantação)
     → item permanece `received`, recibo `received` com reason_code
       TEAT.SYNC_DESTINATION_NOT_WIRED { entityType }; a resposta HTTP do lote continua 200
3. applier.validate(payload) devolve { code, fields[] }
     → recibo `rejected` com o code do catálogo e context { fields[] }
4. applier.apply(item, tx) numa **transação por item**, contendo:
     efeito de domínio  +  sync_queue_item.status='applied'  +  server_entity_id
     +  sync_receipt.status='applied'  +  os eventos do domínio na outbox
5. falha de domínio dentro do apply
     → rollback **completo** da transação do item (nada de efeito parcial)
     → numa transação própria e nova: sync_queue_item.status='conflict'|'rejected',
       sync_receipt com o reason_code, e sync_conflict quando o erro for de divergência
6. invariante: um recibo `received` nunca passa a `applied` sem efeito de domínio commitado
   (route contract §4.3)
```

Tipos aceitos e código de invalidez de cada um (catálogo §1):

```text
entity_type                    applier                        código de validate falho
-----------------------------  -----------------------------  --------------------------------------------
ait                            inf/ait  (M7, §4.6)            TEAT.SYNC_INVALID_CANONICAL_AIT
administrative-measure         inf/measures (CTG-0004)        TEAT.SYNC_INVALID_ADMINISTRATIVE_MEASURE_RECORD
alcohol-signs-term             inf/alcohol  (CTG-0004)        TEAT.SYNC_INVALID_ALCOHOL_SIGNS_TERM_RECORD
ait-cancel-request             inf/ait      (CTG-0001 §4.15)  TEAT.SYNC_INVALID_AIT_CANCELLATION_REQUEST
ait-cancel-posfinal-request    inf/ait      (CTG-0001 §4.15)  TEAT.SYNC_INVALID_AIT_CANCELLATION_REQUEST
crash-record                   nenhum (BOAT, domínio est)     TEAT.SYNC_INVALID_CRASH_RECORD
```

`crash-record` é **reconhecido como suportado** e não tem destino nesta rodada: cai no passo 2 e
fica `received` com `TEAT.SYNC_DESTINATION_NOT_WIRED` (M5). Nunca é `rejected` com
`SYNC_UNSUPPORTED_ENTITY_TYPE` — o cliente móvel do BOAT não deve ser instruído a atualizar.

### 4.4 Recibo × `error_code` × efeito — a tabela do protocolo

```text
recibo     error_code                             efeito de domínio  sync_queue_item  sync_conflict
---------  -------------------------------------  -----------------  ---------------  -------------------
applied    (nulo)                                 sim, commitado     applied          —
received   TEAT.SYNC_LEGACY_ITEM_NOT_APPLIED      não                received         —
received   TEAT.SYNC_DESTINATION_NOT_WIRED        não                received         —
rejected   TEAT.SYNC_UNSUPPORTED_ENTITY_TYPE      não                rejected         —
rejected   TEAT.SYNC_INVALID_CANONICAL_AIT        não                rejected         —
rejected   TEAT.SYNC_INVALID_ADMINISTRATIVE_…     não                rejected         —
rejected   TEAT.SYNC_INVALID_ALCOHOL_SIGNS_…      não                rejected         —
rejected   TEAT.SYNC_INVALID_AIT_CANCELLATION_…   não                rejected         —
rejected   TEAT.SYNC_INVALID_CRASH_RECORD         não                rejected         —
rejected   TEAT.SYNC_INTEGRITY_ERROR              não (rollback)     rejected         integrity
rejected   TEAT.NUMBERING_RESERVATION_FOREIGN_…   não (rollback)     rejected         domain
rejected   TEAT.NUMBERING_NUMBER_ALREADY_APPLIED  não (rollback)     rejected         domain
conflict   TEAT.NUMBERING_RESERVATION_EXPIRED     não (rollback)     conflict         domain
conflict   TEAT.SYNC_CONCURRENCY_SUSPECT          sim, o AIT nasce   conflict         concurrency
                                                  em SUSPEITO_
                                                  CONCORRENCIA (M6)
conflict   TEAT.SYNC_ITEM_CONFLICT                não (rollback)     conflict         domain
```

`sync_receipt.status` ∈ `received | applied | conflict | rejected`;
`sync_queue_item.status` ∈ `pending | received | applied | conflict | rejected`;
`sync_conflict.status` ∈ `open | resolved`; `sync_conflict.conflict_type` ∈
`integrity | domain | concurrency`. O token `concurrency-suspect` do `sync_queue_item.status` da
origem **não existe aqui**: vira `conflict` com `error_code = TEAT.SYNC_CONCURRENCY_SUSPECT`
(M5). Nenhuma dessas colunas tem `CHECK` no DDL 18 — §11.5.

`accepted_items` = número de recibos com status ∉ {`rejected`, `conflict`}, ou seja
`applied` + `received`. Difere da origem, que também excluía `concurrency-suspect`; aqui esse
caso já é `conflict`, então a contagem coincide.

### 4.7 Detecção de concorrência (M6, RN-TEAT-111, AC-TEAT-012-2/5)

```text
janela = ParameterService.get('sync.concurrency_window_minutes')
  linha ausente, ou com source_pending = true e value_json nulo
    → detecção DESLIGADA
    → a resposta do lote traz warnings: ['SYNC_CONCURRENCY_WINDOW_SOURCE_PENDING']
    → nenhum item é marcado; nenhum conflito é aberto
  valor presente (inteiro de minutos)
    → detecção LIGADA

com a janela ligada, para cada item de entity_type='ait' do lote:
  candidatos = ops.sync_queue_item do mesmo tenant e mesmo agent_id,
               com device_id ≠ device_id do lote,
               com status ∈ {pending, received},
               e |candidato.created_locally_at − item.created_locally_at| ≤ janela

  descontar handoff autorizado (AC-TEAT-012-4):
    existe ops.ops_session_handoff h do mesmo agente com
      h.handed_off_at ∈ [min(t1,t2) − janela, max(t1,t2) + janela]
    → o par NÃO é concorrência; o candidato é descartado

  candidatos restantes ≠ ∅ ⇒ marcar **os dois lados** (a norma barra ambos):
    item e cada candidato → sync_queue_item.status = 'conflict',
      error_code = 'TEAT.SYNC_CONCURRENCY_SUSPECT'
    recibo de cada um     → status 'conflict', reason_code
      'TEAT.SYNC_CONCURRENCY_SUSPECT',
      details_json { otherDeviceId, windowStart, windowEnd, windowMinutes,
                     conflictingQueueItemIds[] }
    ops.sync_conflict     → { conflict_type: 'concurrency',
                              reason_code: 'TEAT.SYNC_CONCURRENCY_SUSPECT',
                              retryable: false,
                              allowed_resolution_actions: ['manual_review'],
                              status: 'open' }
    o AIT do item é aplicado em SUSPEITO_CONCORRENCIA — o efeito de domínio ocorre, o
    processamento é que fica barrado (AC-TEAT-012-2: bloqueio, não alerta)
    evento AIT_SUSPEITO_CONCORRENCIA por AIT marcado
```

`windowStart`/`windowEnd` = `item.created_locally_at ∓ janela`, em ISO-8601. A apuração só se
encerra por `POST aits/{id}/concurrency-review` (CTG-0001 §4.8): o conflito de concorrência
**não** aceita `accept_server`, `reject` nem `retry_after_correction` em
`sync-conflicts/{id}/resolve` (§5.13).

## 13. Divergências encontradas

1. **Prefixo das rotas manuscritas de `ops`.** `@Controller('ops')`, `@Controller('ops/evidence')`
   e `@Controller('ops/snapshots')` contra `v1/ops/...` de todo controlador gerado e do route
   contract §4. Corrigido em §1 (CTG-0002 e CTG-0003). Sem a correção, `policy-routes.e2e.spec.ts`
   (M18) reprova a rodada inteira.
2. **`numbering_reservation.status='blocked'` e `ops_homologation.status='cancelled'` sem token
   de workflow.** [WF-TEAT-002] só nomeia RESERVADA/CONSUMIDA/EXPIRADA/CANCELADA e [WF-TEAT-003]
   não modela o cancelamento por auditoria. Ambos são **vocabulário de modelagem**, não token
   canônico, no precedente de R-0006 CTG-0001 §2; o route contract §4.3 e a origem já usam
   `blocked`, e `cancel-by-audit` vem da origem.
3. **Expiração de reserva sem rota nem job.** [WF-TEAT-002] prevê `RESERVADA → EXPIRADA` por
   `valid_until`, e nem o route contract nem as decisões M dão rota ou varredura. Nesta rodada o
   status `expired` só existe por fixture e a expiração é **avaliada na leitura** (`valid_until <
now()` barra o applier, §4.6 passo 3), nunca gravada. `source_pending`. → **OD-T24**.

## 14. Adenda do maestro (Architect, 2026-09-15, após delivery-review-CTG-0002 ciclo 2)

**Ordem canônica do lote — resolução formal da incompatibilidade entre §4.1 passos 7–10 e o `batchId` dos
envelopes transacionais.** O ciclo 1 exigiu `data.batchId` persistido em todo envelope de item, o que é
impossível se `ops.sync_batch` só nasce no passo 9. Decisão do Architect, que **substitui** os passos 5–10 de
§4.1:

```text
passo  ação                                                                              transação
-----  --------------------------------------------------------------------------------  --------------------------
1–4    validação de forma (zod), replay de device_batch_id, guarda de sequência          nenhuma escrita
5      persistir ops.sync_batch { device_batch_id, batch_sequence, submitted_at,          própria (durável)
       accepted_items = 0, receipts_json = { item_ids: [] } } — identidade durável do
       envio; nada de item ainda existe
6–8    por item: materializar sync_queue_item/sync_receipt `received`; aplicar (applier   uma por item (§4.3)
       + promoção pelas portas + eventos, todos com data.batchId = id do passo 5);
       falha → rollback do item + recibo conflict|rejected em transação própria
9      fechar o lote: update ops.sync_batch { accepted_items, receipts_json.item_ids }    própria
10     publicar sync.batch.received (batchId, counts) e responder
```

Consequências que passam a valer como contrato: (a) um lote interrompido entre 5 e 9 **fica durável** com
`accepted_items = 0` ou parcial e `receipts_json` incompleto — isso é desejado: o reenvio do mesmo
`device_batch_id` cai no replay de passo 2 e devolve os recibos já emitidos (recuperação de ACK perdido,
C-0002-27/28), nunca reaplica; (b) `sync_batch` sem itens não é estado inválido (o DDL 18 admite
`accepted_items >= 0`); (c) o replay compara o conjunto de `idempotency_key` dos itens **materializados**
com o lote reenviado — lote interrompido antes de materializar todos os itens e reenviado com o mesmo
`device_batch_id` e o mesmo conjunto é replay legítimo e completa a materialização dos itens que faltam
(comportamento já coberto por C-0002-28 "lote parcial"). A implementação da iteração 3/4 de TASK-0005
segue exatamente esta ordem; nenhum teste muda.

**§14 (d) — ratificação (Architect, após TASK-0005 iteração 5 / OD-T49).** O passo 5 grava em
`ops.sync_batch.receipts_json.declared_keys` o conjunto de `idempotency_key` declarado no envio original
(sem DDL). O replay compara o conjunto reenviado com `declared_keys`: igual → continuação (recibos
existentes sem `apply`, itens faltantes materializados e aplicados, fechamento no passo 9); diferente
(chave a mais ou a menos) ou sequência divergente → 409 `TEAT.SYNC_BATCH_REPLAY_CONTEXT_MISMATCH`.
Linhas legadas sem `declared_keys` (anteriores a esta adenda; só fixtures) usam o conjunto materializado:
materializadas ⊆ reenviadas é continuação; chave materializada omitida → 409. OD-T49 fecha-se por esta
ratificação.
