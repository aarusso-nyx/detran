# CTG-0003 / A3 — proposta Architect para normalização arquivística

**Papel:** Architect (Constituição, Art. 7). **Estado:** proposta para caracterização Inspector e aplicação posterior pelo Engineer/maestro; nenhum TASK histórico, schema, gate ou prova foi alterado por esta proposta. **Autoridade:** OD-R20-007, `work/rounds/R-0020/AUTHORIZATION-A3-2026-09-28.md`, que aceita Q1=A, Q2=A e Q3=A do RGR hashado. A aceitação de Q2 autoriza preparar o mapa por fonte, não determina a semântica dos 54 valores `none`.

## Unidade de migração e invariantes

1. Uma unidade é **um arquivo original** `work/rounds/<R>/tasks/TASK-*.json`, identificado pelo caminho relativo, ID interno, rodada e SHA-256 dos bytes lidos antes da primeira escrita. Nunca normalizar a partir de JSON reserializado como se fosse o original.
2. Para cada unidade efetivamente alterada, gravar antes da TASK canônica um sidecar em `work/rounds/<R>/tasks/_legacy-originals/<nome-original>.raw`. O conteúdo do `.raw` é a sequência integral de bytes do arquivo original, inclusive espaços, quebras de linha e newline final; não é cópia semântica, pretty print ou JSON reparado. A pasta aninhada fica fora da enumeração direta de `verify:round-tasks.mjs`, que lê apenas `tasks/TASK-*.json`. Sidecar existente com bytes ou digest divergentes causa falha fechada; não sobrescrever.
3. Calcular `SHA-256(original bytes)` e `SHA-256(canonical bytes)` independentemente. Usar tags permitidas pelo schema 2.0.0 na TASK canônica, exatamente `legacy-original:<caminho do .raw relativo à raiz da rodada, começando por tasks/_legacy-originals/>` e `legacy-sha256:<64 hex minúsculos>`. O verificador A3 futuro deve exigir **exatamente um par** em cada TASK migrada, resolver o caminho dentro do repo sem `..`/symlink externo, comparar o hash com os bytes do sidecar e conferir que `round_id`, ID original (ou alias registrado) e ID canônico correspondem. As tags são vínculo, não prova suficiente sem essa verificação.
4. O relatório de execução antes/depois fica em `work/rounds/R-0020/reports/A3-migration-before-after.json`, gerado pelo normalizador quando o maestro aplicar a migração. Por caminho original e canônico, deve incluir `round_id`, ID antigo/novo, SHA-256 e tamanho de ambos os arquivos, sidecar, campos transformados, fonte/decisão de cada valor novo, status de schema e razão `source_pending`. Ordenar por caminho; segunda execução não muda bytes nem gera sidecar adicional. O verificador independente lê o relatório para conferir hash canônico e inventário de campos. Em caso de falha parcial, não substituir TASK original sem sidecar já persistido e verificável; operação repetida só prossegue se os hashes esperados coincidirem.
5. Preservar integralmente no sidecar campos rejeitados por `additionalProperties: false`, inclusive `execution_evidence`, `closure_reconciliation`, detalhes legados de `iteration_trail`, `selection.registry_id` e IDs/composições literais. A projeção canônica só pode omitir o campo após verificação do sidecar/vínculo e registro explícito no antes/depois. Dados de prova não são convertidos em novos resultados de execução nem `evidence_refs` fictícios. Campos permitidos, mas semanticamente incompatíveis, ficam `source_pending` até fonte ou decisão específica.
6. `target_invariants`: os tokens que não são `INV-*` podem ir, sem perda de literal, a `tags` como `ref:<token>` pela regra já aceita em CTG-0003. Os quatro `INV-EVIDENCE-001`/`INV-OFFLINE-001` de R-0005 TASK-0002/0003 não constam de `law/trace.json`; permanecem `source_pending`. Não promover ADR, RN, WF ou OD a invariante. Não alterar `law/schemas/task.schema.json` nem enfraquecer `verify:round-tasks`.
7. Cada valor canônico novo exige a fonte exata na tabela `../reports/A3-source-map.md` ou decisão semântica posterior. `source_pending` proíbe a mutação daquele arquivo; o sidecar não torna válida uma escolha de `db_isolation`, disciplina, status, relação de pipeline, executor, título ou ID de composição feita por aproximação. O gate de zero inválidas, `pnpm check` e os selos seguem pendentes até migração completa e verificada.

## Isolamento e limites semânticos

**Adenda A3.1 autorizada em 2026-09-28:** a pendência descrita abaixo para os 54 valores `none` foi resolvida pela decisão prospectiva do Owner em `AUTHORIZATION-A3.1-2026-09-28.md`. A aplicação fica limitada aos 54 pares de caminho e SHA-256 de `CTG-0003-A3.1-none-allowlist.json`. O valor canônico `database` designa somente o limite mínimo caso uma execução futura adquira banco sob a governança atual; não atesta isolamento histórico. As tags `legacy-db-isolation:none` e `legacy-db-policy:prospective-database`, o original byte a byte e o relatório antes/depois são obrigatórios. Os testes Inspector de caminho, hash e sidecar precedem a implementação. As demais classes `source_pending` continuam pendentes; a descrição histórica abaixo documenta o motivo da adenda, sem lhe retirar efeito.

O schema permite somente `database` e `cluster`; **não codifica “sem banco”**. Os 54 `db_isolation: none` são listados individualmente no mapa e ficam `source_pending`: escopo F2/F5, título de frontend, `pnpm check` ou existência de banco na rodada não prova qual isolamento aquela tarefa efetivamente adquiriu. Os dois nomes literais `detran_r7_ctg1_a2` de R-0007 TASK-0079/0081 têm fonte específica no `plan.md` da rodada (banco dedicado e descartável); a proposta é `database`, com o nome literal preservado no sidecar e antes/depois, sujeita à conferência Inspector. Nenhum `none` herda essa conclusão. Se a intenção histórica era **não adquirir banco**, o schema atual não dispõe de valor fiel: requer decisão de especificação/autoridade competente antes do gate zero, sem falsificar `database`.
