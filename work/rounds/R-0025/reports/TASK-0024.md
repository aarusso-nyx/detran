## Julgamento Architect — fixture estrangeira para RLS/404

Leitura: DDL `19-rait-priority-enforce.sql` funções case_guard, consistency e
triggers deferred; DDL34 FKs; ADR-0037. Uma fixture de owner no DB descartável
pode materializar um **contrafactual de tenant para isolamento**, sem alegar que
executou qualificação inicial ou preparou uma jornada produtiva no tenant B.

Para o teste que apenas procura o case estrangeiro e exige 404, não é necessário
instanciar pool/membro/parâmetros do fluxo de qualificação. Usar uma única transação:
caso B novo com legal_priority NULL; assessment canônico outcome none, revision 1,
sem bases, com novos IDs/tenant/case e policy/timezone/data coerentes preservados;
projeção none escrita no papel role_rait_priority_writer e tenant B. Forçar
constraints immediate antes do commit comprova as invariantes ainda ativas.
Não desabilitar trigger, RLS ou imutabilidade, nem adicionar grant/membership.

A FK atual de case para AIT é por id, não composta com tenant. Reusar o ID da
fixture existente não comprova legitimidade de relação AIT cross-tenant. Se a
sonda acessar ou qualificar AIT, criar a correspondente cópia sourceada sob B;
a sonda negativa de lookup de case não prova esse join ou a qualificação.

Persistir fixture de IDs determinísticos idempotentemente no DB dedicado; não
apagar/alterar assessment imutável para teardown. Confirmar row B e consistência
antes da requisição; request usa app role/context A real, comprova invisibilidade
RLS e 404; restaurar role/tenant de preparação. Privilegiado é só setup,
nunca o caminho da requisição. Este julgamento não cria regra de produto.
