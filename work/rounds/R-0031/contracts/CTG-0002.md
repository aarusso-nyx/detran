# CTG-0002 — fixtures e matriz de garantia PEC

**Rodada:** R-0031, O5–O6. **Estado:** checkpoint de Inspector; a cobertura
efetiva de RLS ainda precisa de corretiva antes da publicação de CTG-0002.
Este CTG estende CTG-0001 sem alterar contratos HTTP nem
status/corpos caracterizados. Pela OD-PW-007, envelopes `PEC.*` continuam
diferidos até haver caracterização HTTP viável.

## 1. Fonte de verdade para autorização

Cada operação PEC deve testar autorização por cálculo, nunca por uma lista de
papéis copiada neste documento:

```ts
const policyKey = `ch:${resource}:${action}`;
const grants = DETRAN_POLICY_MATRIX[policyKey] ?? [];
const canonicalRoles = DETRAN_ROLES;
const hasGlobalGrant = (role: DetranRole) =>
  permissionsForRoles([role]).includes('*') &&
  policyKey !== 'ch:retention:review';
const denied = canonicalRoles.filter(
  (role) => !grants.includes(role) && !hasGlobalGrant(role),
);
```

`DETRAN_ROLES`, `DETRAN_POLICY_MATRIX` e `permissionsForRoles` são importados
de `backend/domains/shared/src/{roles,policy}.ts`. Assim, cada operação
coberta tem exatamente um caso positivo para **cada** grant expresso e para a
autorização global que a política declara, além de um 403 para cada outro papel
canônico, inclusive papéis não PEC. O caso positivo usa um principal de um só
papel. A expectativa 403 é uma negação de autorização, sem corpo, status ou
envelope inventado.

Uma ausência de chave `ch:${resource}:${action}` na matriz é falha de contrato,
não autorização implícita. A exceção de `retention:review` mantém a exigência
específica de `DPO` definida em `isDetranActionAllowed`.

`retention:review` permanece exceção restrita a `DPO` em
`isDetranActionAllowed`, antes do atalho global. A matriz deriva essa regra do
resultado da política, sem transcrever papéis globais nem ampliar `policy.ts`.

## 2. Oráculo comum de segurança

Além da matriz de papéis, a suíte de cada módulo pertinente deve aplicar estes
oráculos ao recurso e operação correspondentes:

| Oráculo    | Prova requerida                                                                                                  |
| ---------- | ---------------------------------------------------------------------------------------------------------------- |
| tenant     | principal do tenant A não lê/muta recurso B e principal B não lê/muta recurso A; sem existência revelada         |
| titular    | `CANDIDATO` só obtém o seu dossiê via vínculo de identidade; sua leitura não mascara os campos do próprio dossiê |
| Suporte    | autorização global atual ainda exige serialização mascarada; tentativa negada pela política devolve 403          |
| assinatura | provedor/porta indisponível falha fechada; não emite laudo nem simula recibo de assinatura                       |
| integração | RENACH, biometria, TSA e toxicologia são portas/mocks; nenhum teste usa integração externa real                  |

`candidate-dossier` é uma operação da superfície C que R-0032 consumirá. Nesta
rodada ela é apenas uma expectativa de contrato e fixture; nenhuma rota Portal
ou política é modificada.

## 3. Matriz dos 17 módulos `ch`

Cada linha aplica a regra de §1 a todas as operações `ch` daquele módulo que
constem de CTG-0001 e de seu contrato manual. “Ciclo” descreve a prova de
fixture, sem criar token de estado que a fonte ainda não publicou.

| ---------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |

| `clinical-controls`    | controle clínico criado/lido/escrito conforme contrato           | tenant obrigatório; dado clínico do titular não vaza para Suporte; sem assinatura substituta                                    |

## 4. Casos de ciclo transversal

1. P-01 cobre agendamento por região/data sem escolha de clínica ou perito.
2. P-02 cobre resultado e dossiê próprio sem máscara, laudo e adendo de dupla
   aprovação.
3. P-03 cobre restrição com conteúdo ainda disponível e valor normativo ausente
   marcado `source_pending`.
4. P-04 cobre pedido de junta cujo prazo vem do catálogo de parâmetros.
5. P-05 cobre recurso para CETRAN/colegiado distinto.
6. P-06 cobre recebimento toxicológico positivo, negativo e inválido através de
   adaptador simulado.
7. P-07 cobre direitos do titular e a disposição de retenção `BLOCKED`, sem
   SQL de deleção.
8. A transmissão tem variantes `ACKED` e `ERROR`; o fechamento do encounter
   exige o primeiro e o segundo permanece reprocessável pelo backend.

## 5. Critérios de aceite do CTG

1. As fixtures seguem `ARCH-PEC-FIXTURES`, compartilham o token de CPF/hash com
   R-0032 e não contêm CPF válido, biometria real ou integração externa.
2. Para toda operação PEC contratada, os testes derivam grants e negativos de
   `roles.ts`/`policy.ts`; todo papel canônico sem grant de rota ou global
   recebe 403.
3. Os 17 módulos possuem prova de ciclo aplicável, isolamento tenant e a regra
   titular sem máscara/Suporte mascarado ou 403, conforme a concessão expressa.
4. Indisponibilidade de assinatura não emite laudo; retenção não elimina dados;
   toxicológico inválido não muda o registro do condutor.
5. Prazos, estados, códigos e corpos HTTP sem fonte continuam
   `source_pending`; esta tarefa não introduz envelope `PEC.*`.

## 6. Checkpoint O5 (2026-09-29)

`TASK-0005` consumiu as duas iterações previstas. A spec de `patients`
comprova leitura e mutação A/B sob `role_app_backend`; as outras oito specs
clínicas só comprovam `relrowsecurity` no catálogo e reutilizam esse oráculo
para `patient`. `TASK-0006` também consumiu duas iterações: `billing` comprova
`billing_invoice` A/B, enquanto as outras sete specs regulatórias apenas
consultam o metadado RLS. Portanto os critérios 2–4 não estão aceitos para os
15 recursos remanescentes. Uma tarefa corretiva de Inspector, posterior à
semente O6, deve criar fixtures sintéticas e provar RLS por tabela sem tocar
os adaptadores protegidos de assinatura.
